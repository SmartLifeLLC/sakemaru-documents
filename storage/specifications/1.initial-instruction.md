
# 「酒丸帳場」開発仕様書

---

## 1. プロジェクト概要

本プロジェクトは、請求書および関連証憑を電子帳簿保存法（電帳法）に準拠した形式で保存・管理・共有するためのプラットフォーム「酒丸帳場」を構築するものです。
企業（管理者）とその取引先（Partner）が、双方で発生した請求書を一元管理できるシステムを目指します。

### システム構成
- **管理者用パネル (`/admin`):** 請求書の発行、受領、取引先管理を行う。
- **取引先用パネル (`/partner`):** 自社宛請求書の閲覧、および自社証憑の保管を行う。

## 3. インフラ・アーキテクチャ要件

### 3.1 データベース構成
**DB分離型（Single Tenant）** を採用します。
各導入企業ごとにデータベースは独立しますが、システム内に「テナント情報」を持つテーブルを1つだけ保持し、S3パスの識別子として利用します。

### 3.2 ストレージ構成 (AWS S3)
**S3共有型（Multi Tenant Storage）** を採用します。
全クライアントで同一のバケットを使用しますが、プロジェクト専用プレフィックス(`documents`)とクライアントIDにより厳格に分離します。

* **Bucket Name:** `sakemaru-{env}` (e.g., `sakemaru-dev`, `sakemaru-prod`)
* **Directory Structure (S3 Key):**
    ```text
    documents/{client_id}/{owner_dir}/{year}/{month}/{filename}
    ```
    * `documents`: 本プロジェクト用のルートプレフィックス
    * `{client_id}`: `clients`テーブルのID（環境内で唯一）
    * `{owner_dir}`: 取引先ID (`partner_id`) または 自社(`0`)
    * `{year}/{month}`: 取引年月日ベース
    * `{filename}`: 命名規則 `category_date_partner_amount_uuid.pdf`

## 4. データベース設計要件

### 4.1 `clients` (テナント識別)
* **概要:** S3パスを決定するための識別子。本環境では**1レコードのみ**存在する。
* **Columns:** `id`, `name`, `created_at`

### 4.2 `partners` (旧: customers / 取引先ユーザー)
* **概要:** `/partner` パネルへログインする取引先ユーザー。
* **Columns:**
    * `id`: PK
    * `name`: 取引先名/担当者名
    * `email`: ログインID (Unique)
    * `password`: Hash
    * `sales_code`: 基幹システム連携用コード
    * `is_active`: bool (ログイン制御)

### 4.3 `documents` (旧: invoices / 証憑データ)
* **概要:** 電帳法要件を満たすメタデータを含む書類管理テーブル。
* **Columns:**
    * `id`: PK
    * `client_id`: FK (`clients.id`)
    * `partner_id`: FK (`partners.id`) - Nullable (Null=自社管理分)
    * `category`: Enum (`issued`:発行, `received`:受領)
    * `source_type`: Enum (`system`:連携, `manual`:手動)
    * `transaction_date`: Date **[検索要件]**
    * `partner_name`: String **[検索要件]**
    * `amount`: Decimal **[検索要件]**
    * `s3_path`: S3フルパス
    * `file_hash`: SHA-256 **[真実性要件]**
    * `status`: Enum (`draft`, `published`, `archived`)

### 4.4 `audit_logs` (監査ログ)
* **概要:** 訂正削除履歴の確保。
* **Events:** Login, View, Download, Upload, Publish, Delete(Logical)

## 5. 機能要件 (Filament Panels)

### 5.1 Admin Panel (`/admin`)
管理者（導入企業担当者）向け機能。

1.  **Dashboard:** 直近のアップロード状況、未処理書類の確認。
2.  **Documents Resource (書類管理):**
    * **タブ切り替え:** 「発行（連携/手動）」「受領」でビューを分ける。
    * **新規登録（手動）:** PDFアップロード＋メタデータ入力（日付・金額・取引先）。
        * 保存先として「自社用」か「特定Partner用」かを選択可能にする。
    * **発行機能:** ステータスを `published` に変更し、Partner側での閲覧を許可する。
    * **削除制限:** 物理削除は禁止。論理削除のみとし、ログを残す。
3.  **Partners Resource (取引先管理):**
    * アカウント作成、停止(`is_active`)の管理。

### 5.2 Partner Panel (`/partner`)
取引先（顧客）向け機能。

1.  **Documents Resource (受領・保管):**
    * **Scope:** `partner_id` が自身のIDであるレコードのみ表示。
    * **受信トレイ:** 管理者から `published` された請求書を閲覧。
    * **自己保管:** Partner自身が他社からの請求書をアップロード・保管する機能（`category=received`）。
2.  **検索機能 (電帳法対応):**
    * **必須:** 「取引年月日」「取引金額」「取引先名」による複合検索および範囲指定検索。
3.  **プレビュー・ダウンロード:**
    * ブラウザ上でのPDFプレビュー。
    * 操作時の監査ログ記録。

## 6. 電子帳簿保存法対応の実装ルール

本システムは「電子取引データ保存」および「スキャナ保存」の要件を満たす必要があります。

1.  **真実性の確保 (改ざん防止):**
    * **S3 Versioning:** ファイルの上書き時はS3のバージョン管理機能を利用し、過去データを保持する。
    * **Hash保存:** アップロード時にSHA-256ハッシュを計算しDBに記録する。
    * **訂正削除の記録:** `audit_logs` テーブルへ全ての変更操作を記録する。

2.  **可視性の確保 (検索機能):**
    * FilamentのTable Filterを使用し、常に以下の条件で検索可能にする。
        * **日付:** 範囲検索 (From/To)
        * **金額:** 範囲検索 (Min/Max)
        * **取引先:** 部分一致

3.  **ファイル命名規則:**
    * S3上のファイル名重複および管理の明確化のため、以下の命名規則をServiceクラスで強制する。
    * `{category}_{ymd}_{partner}_{amount}_{uuid}.pdf`
